# ADR-047: Scene canvas → output slices, with edge blending and scene crossfades

**Date:** 2026-09-27
**Status:** Accepted (owner: "get this development done"). Reserved by the foundation audit, 2026-09-25, as the top recommended next capability.
**Deciders:** Jones

## Context

Today a scene is assigned to at most one output (ADR-039). Its quads live in that output's normalized [0, 1] space, and each output draws its scene once per frame into its own frame texture (ADR-054).

Three things a live-event rig needs cannot be done:
- **Blending projectors.** Two or more projectors cannot share one wide or tall image with soft blended overlaps. That is standard in every competing tool, and the biggest capability gap in the audit.
- **Output-side correction.** An output cannot show just part of a scene, or warp its whole image (a projector that is slightly off-axis), without moving every quad.
- **Scene crossfades** (PRD US-105) need a composite stage where two scenes' images can be mixed.

TD-12 (per-output vsync) also belongs here.

## Decision

1. **Each scene has a canvas** in pixels.
   - Its quads and objects live in canvas space, normalized [0, 1] as today, so existing geometry needs no conversion.
   - A new scene's canvas takes its first output's resolution. Old files get the assigned output's resolution, or 1920×1080 when unassigned.
   - The canvas size is editable in the Scenes panel; quads keep their normalized positions.
2. **Each output shows slices of one scene.** The routing turns around: an output picks its scene, and several outputs may show the same scene. Old files map scene.assignedOutputId to output.sceneId.
   - A **slice** has:
     - an input rectangle on the canvas, in pixels;
     - an output warp: four corners in the output's normalized space, optionally a grid through the ADR-049 evaluator;
     - edge blend zones for left, right, top and bottom, each with width in pixels, gamma and a curve;
     - an optional black-level lift for the overlap.
   - An old file gets one full-canvas slice per output with no warp and no blend, which renders exactly as today.
   - Slices are edited in an Output panel slice editor, with the same keyboard model for the warp corners: Tab, the arrows, Shift and Alt.
3. **Auto-blend.** When two or more outputs show the same scene and their slices overlap on the canvas, one action sets matching blend widths on the facing edges. Values stay editable, and a blend test pattern is available.
4. **Rendering.**
   - Each scene that at least one output shows is drawn once per frame into a canvas texture at canvas resolution.
   - Each output then composes its slices from that texture into its frame texture (ADR-054) with a slice shader: warp, blend ramp, gamma, black level.
   - The output windows and previews are unchanged.
   - 3D objects render per output through that output's ProjectorCamera straight into the output frame, as today. Calibration is per projector, so objects are not drawn through the canvas.
   - Blackout and missing-media black apply as today.
5. **Scene takes and crossfades.**
   - A take (keys 1–9, OSC, MIDI) swaps the scene on every output that currently shows the active scene, so a blended group changes together.
   - Takes can carry a fade time: global in Preferences, per take through OSC `/qm/scene/take i n f seconds`, default 0 = cut. During a fade both scenes' canvases render and the slice shader mixes them. Audio follows the audibility rule, with both scenes audible and cross-gain ramped during the fade.
6. **Per-output presentation (TD-12).**
   - Measure first. If a second fullscreen projector tears with interval 0, present outputs that share a refresh rate with vsync from the single present point, and pace outputs at other refresh rates independently, e.g. one present thread per output that swaps the already composed frame.
   - GL composition stays on the main thread.
   - The chosen design and its measurements go in an amendment.
7. **Persistence.** `.qmap` 3.4 adds the scene `canvas` and output `sceneId` and `slices` fields. Readers accept 3.x. Old files load as described above and render identically; a fixture proves it.
8. **Gates.**
   - Pixel identity: an old show renders byte-identically on its outputs (readback).
   - Blend correctness: in a two-output overlap, the sum of the linear-light contributions is flat within 2% across the overlap for gamma 2.2.
   - The success-metric workflow is unchanged.
   - Takes change blended groups together, and `sameFrame` still passes.
   - A 1 s crossfade is smooth: no frame repeats, and the mix is monotonic.
   - `--bench=quads256` on 2 outputs stays ≥ 60 fps with p99 ≤ 16.7 ms on a quiet machine, with the extra canvas pass.

## Consequences
- ✅ Multi-projector blended shows, output-side keystone and scene crossfades.
- ✅ Old shows behave exactly as before.
- ❌ One extra render pass per shown scene: a canvas-sized texture, 8 MB at 1080p.
- ❌ Routing turns around (output → scene), touching the Scenes panel, scene takes, OSC and serialization; all covered by tests.

## Alternatives considered
1. **Blend per quad** (soft edges already exist, ADR-037). Rejected: it cannot blend two projectors showing one continuous image.
2. **One global canvas for the whole show.** Rejected: separate scenes per output, from ADR-039, remain a valid workflow.

## Amendment 1 (part A implementation, 2026-09-27, QM-120)
Part A (§1, §2 data model, §4 rendering, §5 takes without fades, §7 persistence, the gates) is built. Part B is QM-121.
- **Model.** `Scene` has a canvas size in pixels (default 1920x1080, clamped to 16384). `Scene::assignedOutputId` and the scene-list routing helpers were removed: the routing is on the output (`OutputWindow::sceneId`), and each output holds its `Slice`s (`scene/Slice.hpp`). A slice is an input rectangle in canvas pixels, a warp (an ordinary `QuadGeometry` in output space, so a grid warp goes through the ADR-049 evaluator and `MeshSubdivision::generateMesh`), four `BlendEdge`s (width in canvas pixels, gamma, curve) and a black level. `OutputManager::showScene` routes a scene: an output without slices gets one full-canvas slice; existing slices are rescaled when the canvas size changes, so they keep their place on the picture.
- **Blend ramp.** Linear-light ramp f(t) = ½(2t)^p below ½, 1 − ½(2(1 − t))^p above, with p the edge's curve (default 2), so f(t) + f(1 − t) = 1 for any p. The pixel gain is f^(1/gamma), the product over the four edges. The black level is a lift `L + (1 − L)·c`, applied only outside every blend zone (a step, not a ramp). The shader and `sliceBlendGain` share the formula.
- **Rendering.** `OutputManager::renderOutputFrames` draws each scene that an output shows once into its canvas (RGBA8, cleared to transparent, colour blended exactly as before, coverage accumulated in alpha), then for each output: black clear, the scene's 3D objects through that output's projector, then its slices composited with (ONE, ONE_MINUS_SRC_ALPHA). The ADR-054/QM-115 ordering and blackout are unchanged; in blackout no canvas is drawn. Canvases are keyed by scene, reused across frames, released when no output shows the scene, when its last output is deleted and at shutdown. No per-frame allocation after the first frame.
- **Deviation: the canvas is drawn in its outputs' rotation.** When every output showing a scene has the same rotation the canvas is rasterized already turned (as the frame was before canvases), and the slice shader maps into it; with mixed rotations it is drawn unturned. Without this, a rotated projector differed by up to 2 levels at many pixels because the quads were rasterized in another orientation.
- **Deviation: exact-copy path.** An unwarped slice whose input is exactly the frame's effective size and starts on a pixel boundary fetches the texel under each pixel (`texelFetch`), with no filtering. Other slices sample bilinearly.
- **Gate a (pixel identity), measured by readback** (`RenderOnceReadbackTest`, the ADR-054 feature scene: keystone, bezier, mesh warp, crop, colour correction, soft edge, translucency, plus a 3D cube): with no 3D object, byte-identical at 0/90/180/270 degrees; in blackout, identical. With the cube, every pixel is identical except where a translucent quad lies over the cube: about 410 of 16,896 pixels differ by at most 2 levels (1 at 0 degrees). The old path blended the quad straight onto the object; the canvas blends it into 8 bits first and composites that over the object, two roundings instead of one. Objects cannot go through the shared canvas because each projector sees them from its own camera. Accepted; a 16-bit canvas would fix it but can break exactness for the common no-object case.
- **Gate b.** `SliceTest.TwoOutputOverlapSumsToFlatLinearLight` (maths, < 1e-4) and `CanvasSliceRenderTest.TwoOutputOverlapSumsToFlatLinearLight` (GPU readback, 8-bit frames, gamma 2.2, 128 px overlap): worst |sum − 1| = 0.0053, within the 2% gate.
- **Gate c/d.** The keyboard-workflow tests are unchanged and pass. Takes: if an output already shows scene N it just becomes active (unchanged); otherwise N replaces the active scene on every output that shows it (the blended group); with none, on the first enabled output. `SceneTakeTest.BlendedGroupChangesTogether`, `SceneTakeRoutingTest.*`; the `sameFrame` bench scenario is unchanged.
- **Gate e (bench).** Release `--bench=quads256 --bench-outputs=2` ran on a busy machine (another agent compiling, CPU 54–100%): 1 output 48.6 fps, p99 98.9 ms; 2 outputs 67.1 fps, p99 44.7 ms. Not a quiet-machine result; the ≥ 60 fps / p99 ≤ 16.7 ms gate still needs a quiet rerun.
- **Migration.** Files before 3.4: output.sceneId comes from the (first) scene whose assignedOutputId named it; that scene's canvas is the output's effective (rotated) resolution, else 1920x1080; the output gets one full-canvas slice. Outputs no scene named show nothing and get no slice (the ADR text says one slice per output; an unrouted output has nothing to slice, and `showScene` gives it one when it is routed). `.qmap` 3.4.0 still writes scenes[].assignedOutputId (first output showing the scene) so 3.0–3.3 readers keep their routing. Fixture `v3.4-canvas-slices.qmap`; every older fixture is checked to migrate to one unwarped, unblended full slice.
- **Canvas follows a lone output.** Until part B's canvas-size editor exists, a scene shown by one output alone through its untouched default slice, whose canvas equals that output's effective resolution, follows a resolution or rotation change (`OutputManager::followOutputSizes`), so single-projector shows behave as before. A new scene takes the first output's effective resolution.
- **UI (minimal).** Scenes panel: per scene, a combo of the outputs showing it (each entry toggles). Inspector (selected output): a Scene combo. The editor canvas aspect is now the scene's canvas.
- **Not in part A (QM-121):** slice editor with the Tab/arrow/Shift/Alt corner keys, auto-blend, blend test pattern, canvas size editing, crossfades (§5 fades), TD-12 presentation (§6). Calibration still assumes an output shows its canvas unwarped at 1:1; with offset or warped slices, calibration points are in projector pixels while the canvas is not.

## Amendment 2 (review fixes to part A, 2026-09-27, QM-120)
A fresh-context review found routing bugs that put the wrong picture on a projector during routine operator actions. What changed from Amendment 1:
- **Slices remember their canvas.** An output keeps the canvas size its slices were made for (`OutputWindow::slicesCanvas`) and `showScene` rescales from it, so slices kept through "(no scene)", a Scenes-panel toggle-off or a deleted scene land right on the next scene. Slices of an unknown canvas are replaced by one whole-canvas slice. Deleting a scene takes it off every output showing it. An output that shows no scene is saved with no sceneId and no slices, because its rectangles belong to a canvas the file would not name.
- **Take fallback.** When no output shows the active scene (it was just added, or clicked in the Scenes panel), a take goes to the first enabled output **and every output that shows the same scene as it**, so a blended group still changes together. This replaces "with none, on the first enabled output".
- **Canvas adoption.** Operator routing (Inspector, Scenes panel, takes, and the route a v1/v2 file gets on load) goes through `OutputManager::routeScene`: when the output is the only one showing the scene, through its default slicing, the canvas takes the output's effective (rotated) resolution. The picture is not resampled, and the editor and 3D preview have the projector's aspect. Quads are normalized, so the projector shows the same geometry. Groups and edited slices keep their canvas.
- **Migration.** A pre-3.4 scene no output shows gets the first output's effective resolution; only a file without outputs gets 1920x1080. A 3.4 output with a sceneId and no slices gets one whole-canvas slice at load.
- **F11.** Entering and leaving perform mode sets the output to the monitor's mode, then restores it. A lone default canvas still follows, but `followOutputSizes` does not report a change that comes with an output going fullscreen or back, so perform mode no longer marks an unchanged show modified.
- **Black level.** The lift outside the blend zones is `L + (1 − L)·(canvas over what is already in the frame)`: colour `L + (1 − L)·c.rgb`, alpha `1 − (1 − L)(1 − c.a)`. Alpha 1 had replaced the 3D objects under a lifted slice with black. `CanvasSliceRenderTest.ShaderMatchesSliceBlendGainOnEveryEdge` ties the shader to `sliceBlendGain`/`outsideBlendZones` per pixel (worst 1 level).
- **Canvas target.** The canvas is colour only; 3D objects render per output, so a depth buffer went unused (about 16 MB per scene at 1080p). `MAX_CANVAS_DIMENSION` is 8192, the texture size every GL 3.3 (Direct3D 10 class) GPU supports, applied on create and load (was 16384, 2 GiB with depth). A canvas above `GL_MAX_TEXTURE_SIZE`, or one the GPU runs out of memory for, is logged once and not retried until its size changes. Its outputs then show their 3D objects but no quads.
- **Rescale.** `rescaleSlices` scales edges in double and snaps an edge within 1/1000 px of a whole pixel onto it, so a whole-canvas slice stays exactly whole (float had given 1920.0001 for 800 → 1920) and keeps the exact-copy path.
- Gate a (`RenderOnceReadbackTest`) and gate b are unchanged and pass.

## Amendment 3 (part B1 as built, 2026-09-27, QM-121)
Part B1 is the editor side of part B: the slice editor, the warp keys, auto-blend, the blend test pattern, canvas size editing and the canvas lock. Crossfades (§5 fades) and TD-12 presentation (§6) are part B2, built separately.
- **Where the slice editor is.** A "Slices" section of the Properties panel for the selected output (Outputs tab, then the output), not a separate panel. The output's scene, resolution, rotation and calibration are already edited there, and it shows one output at a time, which is what a slice list belongs to. It lists the output's slices (add a whole-canvas slice, remove, select) and edits the selected one: name, input rectangle (x, y, width, height in canvas pixels), the four warp corners (numbers), the four blend edges (width, gamma, curve) and the black level. Scene-wide actions sit below it: Auto-blend and the blend test pattern. While an output is selected, its slices' input rectangles are outlined on the editor canvas (the selected one brighter). The input rectangle is edited with numbers only; dragging it on the canvas would compete with clicking and dragging quads there.
- **Warp editing on the canvas.** "Edit Warp on Canvas" puts the canvas in slice warp mode, like calibration mode: the canvas shows the output's frame (its effective aspect), its slices drawn from the scene's canvas texture with the same slice shader (`slice.vert` now takes the editor view transform, identity for output frames), every slice's warp outline, and the selected slice's corner handles drawn by `Renderer::renderCornerHandles`. The mouse drags a corner (one undo step on release) and the canvas keys follow the quad model: Tab / Shift+Tab cycles the corners, the arrows nudge by `nudgeStep` (Shift 10×, Alt 0.1×), with `cycleVertex`, `readCanvasKeys` and `claimCanvasEditingKeys` from `VertexKeyboard.hpp`. Quad editing is suspended (no hit-test, no Delete, Ctrl+A or z-order keys on quads); Esc or the button leaves the mode; it ends by itself when its output or slice goes, and cannot run during calibration. Who gets the canvas keys is one function, `canvasKeyOwner` (`app/SliceEditing.hpp`): calibration, else slice warp mode, else the selected quad. Selecting a slice in the editor alone never takes the keys from a quad. The quad corner-pin keys moved into `applyCornerKeys` (`app/MeshEditKeys.hpp`, beside `applyMeshEditKeys`) unchanged, so the same code runs in ViewportEditor and in the tests.
- **Undo.** Every slice edit is a `SliceEditCommand`: the output's slice list (and the canvas size it was made for) before and after, resolved by output id through `OutputResolver::readSlices` / `writeSlices`, so a removed output makes it a logged no-op. Edits with the same key on one output merge into one step: one warp corner (keyboard, mouse and the corner fields share the key), one blend field of one edge, the input rectangle, the black level. Auto-blend and canvas resize are compound steps. Every edit marks the show modified; slices were already saved (3.4).
- **Auto-blend.** `autoBlendEdges` pairs slices of different outputs whose input rectangles overlap. Two slices face left/right when one lies further left than the other (neither spans the other horizontally) and they share at least half of the shorter one's height; top/bottom likewise. A corner-only overlap (a 2×2 grid's diagonal) faces neither way; when both directions qualify, the narrower overlap wins. A facing edge gets the overlap's width with gamma 2.2 and curve 2; other edges keep their values; an edge facing several slices takes the widest overlap. Slices of one output never blend with each other. One undo step for the whole scene. Tests: `AutoBlendTest.*` (horizontal pair, vertical pair, 2×2 grid, non-overlapping, partial vertical offset, one output), `SliceEditingTest.AutoBlendSetsTheFacingEdgesAsOneUndoStep`.
- **Blend test pattern.** `OutputManager::setBlendTestPattern` draws every canvas as opaque black with a 16 × 9 grid of white lines and two solid white bands through the middle (one across the full width, one down the full height, so every left/right overlap crosses the first and every top/bottom overlap the second) instead of its scene's quads. The outputs show it through their slices and blend zones; 3D objects are covered. It is session state, never saved. While it is on, the slice editor's button reads "Blend Test Pattern: ON" in orange and an orange banner across the bottom of the editor canvas says the projectors show the pattern, not the show. Test: `CanvasSliceRenderTest.BlendTestPatternReplacesTheSceneOnTheOutputs` (GPU readback).
- **Canvas size.** The Scenes panel shows the active scene's canvas width and height, applied when a field is left, clamped to 1..8192 as on load. Quads keep their normalized positions; the slices of every output showing the scene are rescaled with `rescaleSlices` from the canvas they were made for; one undo step (`SetSceneCanvasCommand` plus a `SliceEditCommand` per output; since Amendment 5, the command alone).
- **Canvas lock (resolves the Amendment 2 question).** Rule: *once the operator sets a scene's canvas size, routing never overwrites it.* Editing the size sets `Scene::isCanvasLocked`; `routeScene` (Inspector, Scenes panel, takes, v1/v2 load routing) and `followOutputSizes` (resolution, rotation, F11) then keep the size even for a lone output through its default slice. A "Fixed" checkbox next to the size turns the lock off again (an undo step), after which a lone default-sliced output adopts its resolution at the next routing or size change, as in part A. `.qmap` 3.4 gains `scenes[].canvasLocked`, written only when true; a file without it loads unlocked, so every existing file behaves as before. 3.4 is unreleased, so the version stays 3.4.0. Tests: `OutputManagerTest.ALockedCanvasIsNeverAdopted`, `ProjectFixtureTest.CanvasLockDefaultsOffAndRoundTrips`, `SliceEditingTest.CanvasResizeRescalesSlicesLocksAndUndoes`, `SceneCommandsTest.SetSceneCanvasCommandSetsSizeAndLockAndUndoes`.
- **Calibration is restricted, not converted (TD-29).** Calibration picks projector pixels on the editor canvas and draws the 3D objects there through the projector, which is only right when the canvas is the projector's frame. Making it correct for an offset or warped slice means the calibration view would show the output frame (slices, warp) with the objects drawn in projector space, and mapping each pick through the slice's warp inverse; that is a redesign of the calibration view, not bounded work. So an output whose scene is shown through anything but its default slicing (one whole-canvas slice, no warp, no blend, no black level) cannot enter calibration: `EditorState::canCalibrate` refuses it, the Inspector button and the Edit menu item are disabled with the reason in a tooltip and a line of text, and the slice editor is disabled for the output being calibrated. Calibrate first, then slice. Test: `SliceEditingTest.CalibrationOnlyWithTheDefaultSlicing`.
- **Tests for the keyboard.** `SliceEditingTest.QuadKeysAreUnaffectedWhileTheSliceEditorIsNotActive` (a slice selected in the editor, warp mode off: Tab, Shift and Alt nudges move the quad and no slice) and `SliceEditingTest.SliceWarpTakesTheCanvasKeysOnlyWhileOn` (Tab / Shift+Tab, 1×/10×/0.1× nudges, one undo step per corner, keys back to the quad when it ends). The existing keyboard tests are unchanged and pass.

## Amendment 4 (part B2: scene crossfades and per-output presentation, 2026-09-27, QM-121)
Part B2 builds §5 (crossfades) and §6 (TD-12). Part B1 (slice editor, auto-blend, test pattern, canvas size, calibration) is Amendment 3.

**Crossfades (§5).**
- **Fade times.** Preferences > General > Scene takes > Crossfade (seconds), 0 to 60, default 0 = cut; used by the 1-9 keys, MIDI and `/qm/scene/take n`. `/qm/scene/take i n f seconds` carries its own time (int or float; above 60 clamped; negative, non-finite, non-numeric or a third argument is a bad argument and takes nothing). A control target may take its whole OSC argument list (`ControlTarget::applyOscArgs`); only this one does. The bench and stress harnesses always cut.
- **State.** `SceneFades` (`scene/SceneFade.hpp`, pure): one fade per output, from the scene it showed (null = nothing, so it fades in from black) to the scene it shows now. The mix is linear in time on the frame clock: steady wall time sampled once per frame in `presentFrame` (`OutputManager::setFrameTime`), never a frame count. Finished fades end at the start of the next frame (`retireSceneFades`), so the audio of that frame is already the cut state.
- **Take during a fade**, chosen as the simplest rule that never shows something that was not on screen: taking back the scene that is fading out reverses from the current mix, with no jump; taking any other scene completes the fade in progress (the scene fading in is shown in full) and fades from it; a cut ends the fade; taking the scene already fading in changes nothing. The routing rule is unchanged (`planSceneTake`), so a blended group fades together.
- **Ends early.** Deleting either scene, deleting the output, or re-routing it by hand (Inspector, Scenes panel) ends the output's fade at once. Blackout hides a fade but its clock runs on.
- **Rendering.** During a fade the scene fading out keeps its canvas (drawn, rotated and released like any shown scene's). `renderSlice` takes an optional `SliceFade` and slice.frag samples both canvases at the same normalized canvas point (texel-exact when both are the frame's size and turn, filtered otherwise) and mixes them before the blend zones and black level. The canvases hold colour premultiplied by coverage, so the linear mix is itself a canvas, and the blend gain and black level apply to it exactly as to one scene (`SceneFadeRenderTest.BlendZonesAndBlackLevelApplyToTheMix`: within 1 level of a scene of the mixed colour). With no fade the uniform is 1 and the branch is skipped, so gate a is unchanged.
- **3D objects** cannot mix through the canvas (each projector sees them from its own camera). During a fade both scenes' objects are drawn with their opacity scaled by their weight, the outgoing ones first with the depth buffer cleared between the passes. Where objects of the two scenes overlap on screen this is not an exact dissolve (the second pass blends over the first); objects of one scene, the usual case, dissolve exactly.
- **Audio** follows the audibility rule. A scene's weight is 1 when it is active or shown by an enabled output; during a fade on an enabled output the outgoing scene is at cos(mix·π/2) and the incoming one at sin(mix·π/2). Equal power, because two different soundtracks are uncorrelated and their powers add (cos² + sin² = 1); a linear fade dips 3 dB at the middle. A source used by both scenes is one sound, so its gain is the sum of its scenes' weights capped at 1 and it stays at full level. The gain multiplies the source's volume on the control thread; the mixer already ramps each source's gain linearly across every buffer, so there is no new audio-thread state and no click. At the end the outgoing scene is gated (muted) exactly as a cut does.
- **OSC feedback** reports the take at its start: `/qm/scene/active` changes when the take routes (ADR-048 feedback samples values on change). No message marks the end of a fade; there is no target for fade progress.
- **Gates.** `SceneFadeTest.OneSecondFadeIsMonotonicWithNoRepeatedFrame` (fake clock, 60 Hz and irregular frames: every frame a new, larger mix equal to elapsed wall time, done in 60 frames); `SceneFadeRenderTest.OneSecondCrossfadeMixesTheCanvasesMonotonically` (GPU readback: t = 0 byte-identical to the old scene, 0.5 within 1 level of the half mix, 1 byte-identical to a cut, 61 frames at 60 Hz strictly monotonic, the outgoing canvas released at the end); `SceneTakeFadeTest.AZeroFadeIsACut`; `RenderOnceReadbackTest` (gate a), `SceneTakeRoutingTest.*` and `bench_smoke`'s `sameFrame` unchanged and passing. Audio: `SceneAudioFadeTest.CrossGainRampsMonotonicallyToZeroAndOne` (weights) and `AppliedGainIsMonotonicClickFreeAndEndsAtZeroAndOne` (the gain `AudioSource::render` applies, 256-frame buffers at 48 kHz against 60 Hz control frames: monotonic, ends at exactly 0 and 1).
- **GUI check** (Debug, `tests/smoke/qa_lib.ps1`): the crossfade set to 1 s in Preferences (saved as 1.0), a two-scene project loaded, F11, key 2: the projector on the second monitor captured mid-fade shows the colour bars and checkerboard mixed, and after 1.5 s the checkerboard alone.

**Per-output presentation (§6, TD-12), measured first.**
- **Hardware here:** the laptop panel, 2560x1440 at 165 Hz on the AMD Radeon iGPU (primary, 150% scaling), and an ASUS VS248, 1920x1080 at 60 Hz on the RTX 3080 Laptop GPU that renders (NVIDIA 610.62, GL 3.3). No second external projector and no two displays at the same rate, so "outputs sharing a refresh rate" could not be measured with two displays.
- **Measurement:** `--bench=present` (opt-in, never part of `all`, since it takes over every monitor): two outputs fullscreen on the two monitors, borderless and exclusive, in both orders, the app's own vsync pacing, 64 animated quads. `OutputManager::lastPresents()` stamps each output's swap as it returns. Per output: swap-to-swap times, a 1 ms histogram, presents per refresh of its display, and swaps closer than half a refresh. DWM's `DwmGetCompositionTimingInfo` counters were sampled too but barely advance here (1 refresh counted in 5 s), so they are not usable on this machine and nothing below relies on them. Tearing cannot be seen from software; the configuration that can tear (interval 0 on an output the compositor does not compose) is reported instead.
- **Before (list order picks the vsync holder; Debug, 2 s per case):** with the 165 Hz panel's output first, it held vsync, the loop ran at 68–80 fps, and the 60 Hz output swapped at interval 0 at 1.14 (borderless) and 1.34 (exclusive) presents per refresh, so a sixth to a quarter of its frames could never be shown; in exclusive mode 19 of its swaps came less than half a refresh apart (the tearing case). With the 60 Hz output first, both presented at 60.0/s, the 60 Hz display at exactly 1.0 per refresh.
- **Decision:** the vsync holder is chosen by refresh rate, not list order (`vsyncHolder(iconified, refreshHz)`): the rate most presented outputs share, a tie to the lower rate, then list order; an output's rate is its monitor's mode in perform mode, unknown for a window. Outputs sharing a rate are therefore paced from the single present point, one new frame per refresh, and no display is sent more frames than it can show. When presented outputs run at different rates the operator is told once which output paces the show and that the others repeat or drop frames.
- **After (Release, 5 s per case, machine loaded by other agents' builds, CPU 58-98%):** in all four cases, whatever the list order, the 60 Hz output holds vsync and presents 0.93-1.0 times per refresh (median gap 16.66 ms); the 165 Hz panel shows each frame about 2.8 refreshes (0.35 presents per refresh). No output is overdriven any more. `VsyncHolderTest.TheSharedThenLowerRefreshRatePacesTheLoop`.
- **Not built: a present thread per output.** It would only swap an already composed frame at the display's own rate. On this machine that cannot help: perform mode is borderless by default, which DWM composes (an interval-0 swap there drops frames but does not tear), and a 165 Hz display fed a 60 Hz show repeats frames whatever thread swaps it. Its one real benefit, an exclusive-fullscreen output at a different rate than the holder, needs two displays at different rates both in exclusive mode and a camera to see tearing. Moving swaps off the main thread also changes context ownership for every output window (WGL contexts current on one thread at a time, the frame textures double-buffered and fenced across threads). Without hardware that shows the problem it would be an untestable threading change, so it stays in TD-12 with its cost.
- **Bench (Release, `--bench=quads256 --bench-outputs=2`, same busy machine: CPU 32-99%, 28 MSBuild processes from other agents):** 1 output 177.3 fps, p99 16.6 ms; 2 outputs 111.2 fps, p99 27.7 ms (40 of 1107 frames over 16.7 ms). Not a quiet-machine result; the p99 gate still needs a quiet rerun.

## Amendment 5 (review fixes to part B1, 2026-09-27, QM-121)
A fresh-context review of part B1 found that undo could put a slice rectangle from one canvas size onto another, plus smaller state leaks. What changed from Amendment 3:
- **Slice undo follows the canvas shown now.** Takes, Inspector / Scenes routing and canvas adoption (`showScene`, `routeScene`, `followOutputSizes`) rescale an output's slices without an undo step, so a `SliceEditCommand` snapshot can be in another canvas's pixels by the time it is undone or redone. The command now rescales its snapshot from the snapshot's canvas to the output's current `getSlicesCanvas()` before writing it, so the projector keeps the part of the picture the step recorded. Two edits with the same merge key no longer merge when the output's canvas changed between them. Tests: `SliceCommandsTest.UndoAndRedoFitTheSnapshotToTheOutputsCanvasNow`, `SliceCommandsTest.EditsAcrossACanvasChangeDoNotMerge`, `SliceEditingTest.UndoAfterATakeToAnotherCanvasFitsTheCanvasShownNow`, `SliceEditingTest.NudgesDoNotMergeAcrossATake`.
- **Canvas size is one command that rescales whoever shows the scene.** `SetSceneCanvasCommand` takes the `OutputResolver` and, whenever it is done, undone or redone, rescales the slices of every output showing the scene at that moment (`OutputResolver::rescaleSceneSlices`). The per-output `SliceEditCommand`s of Amendment 3's compound step are gone, so an output routed to the scene after the resize follows the undo too. `setSceneCanvas` no longer takes the `OutputManager`. Test: `SliceEditingTest.UndoOfACanvasResizeRescalesOutputsRoutedSince`. Crossfades are unaffected: an output's slices are always in the canvas of the scene it shows, the scene fading out is only sampled through them at a normalized point, and an output fading out of a resized scene is not showing it.
- **Leaving warp editing mid-drag keeps the drag.** Esc, the slice editor's button or entering calibration while a warp corner is being dragged used to leave the moved corner with no undo step. `EditorState::endSliceWarp` (and `beginSliceWarp`) now finish the drag first: the corner stays where the operator put it and the move is one undo step, recorded exactly as a mouse release records it (`EditorState::finishSliceWarpDrag`, which ViewportEditor's release also calls). Test: `SliceEditingTest.LeavingWarpEditingMidDragRecordsTheDrag`.
- **Undo is scoped in warp mode as in calibration (TD-17).** While a slice warp is edited on the canvas, Ctrl+Z / Ctrl+Y and Edit > Undo / Redo take only that output's slice steps; any other step is held back with "Leave slice warp editing to undo: ...", so an undo never moves a quad hidden behind the warp view. Test: `SliceEditingTest.WarpEditingUndoesOnlyThatOutputsSliceSteps`.
- **Project replace resets session slice state.** File > New, Open and recovery (`clearProjectContent`, which now takes the `OutputManager`) end warp editing, clear the slice selection, turn the blend test pattern off and end every scene crossfade in progress, so a newly opened show's projectors show the show. Test: `SliceEditingTest.ProjectReplaceEndsSliceEditingTheTestPatternAndFades`.
- **Auto-blend skips the output being calibrated**, whose slicing must stay the default (`canCalibrate`). The slice editor's input rectangle is clamped to the canvas (`clampInputToCanvas`: x and y within the canvas, width and height at least 1 px and no further than its far edge). Tests: `SliceEditingTest.AutoBlendLeavesTheCalibratingOutputAlone`, `SliceEditingTest.InputRectIsClampedToTheCanvas`.
- **Test gaps closed.** Shift+Tab on the quad corner keys (`MeshEditKeysTest.CornerKeysCycleBothWaysAndNudgeWithShiftAndAlt`, and Shift+Tab presses in `SliceEditingTest.QuadKeysAreUnaffectedWhileTheSliceEditorIsNotActive`); a corner-patch overlap that sets nothing (`AutoBlendTest.ACornerPatchOverlapSetsNothing`) and the narrower-overlap tie-break (`AutoBlendTest.WhenBothDirectionsQualifyTheNarrowerOverlapWins`).
